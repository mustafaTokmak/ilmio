## 1. Bottom line

1. **UCP 2026-08-25 has no offer, counter-offer or price message.** The spec's own model for a negotiated price is: the negotiation happens somewhere else, the result is an opaque discount code, and the Business pins that code on the checkout (`ucp.request_constraints`, example titled "Locked negotiated discount codes"). That is idea A, written into the spec. [P]
2. **Free text and vendor data do flow without any capability negotiation** through a fixed set of core fields: business to agent `messages[]`, `links[]`, `policies[]` (custom types allowed, spec example is literally `com.example.policy.price_match`), `totals[]` (custom types), catalog `description`/`metadata`/`tags`, `discounts.applied[].title`, fulfillment option `title`/`description`; agent to business `context.intent`, `context.eligibility`, `attribution`, `signals`, `discounts.codes`, catalog `query`, permalink query fields. [P]
3. **Anything executable is negotiated.** Actions, vendor fields and vendor embedded messages exist only when BOTH profiles declare the same extension at the same version. And a conformant platform must treat all other business text as data, never as an instruction. So free-text channels reach the human through the agent's rendering; they do not make an agent call a tool it was not told about. [P]
4. **A business profile can carry vendor capabilities, and one does today**: Shopware's demo store publishes `com.shopware.quote` and `com.a2cn.negotiation-mandate` next to the `dev.ucp.*` ones. [L] On Shopify the profile is generated by Shopify and holds only `dev.ucp.*` plus Shopify's own `dev.shopify.catalog`. [L] One practitioner reports Shopify blocked his app's name-spaced capability. [S]
5. **A2A is the only binding with free-form natural language in both directions**; Shopify does not offer it (MCP + embedded only). [P][L]
6. **The standards route is open, not closed**: a state-bound Offer extension (#738/#773) is on the 2026-12-08 milestone and was discussed by the Shopping Tech Council on 2 Oct 2026 with "strong industry demand for personalization, reordering, and upselling"; a Quote extension with a buyer `proposal.subtotal` and business `quoted/accepted/declined` (#929/#930) was filed on 11 Oct 2026 by a Google engineer; "approaching discounts" (#482) is on the same milestone; the roadmap lists "Native cross-sell and upsell modules". [P]
7. **AP2 v0.2 has no "intent mandate".** It has open and closed Checkout and Payment Mandates. The price cap lives in the open Payment Mandate and is checked by the credential provider or network, not shown to the merchant. Not a negotiation channel. [P]

## 4. Item (3): how a third-party vendor extension is defined, published, negotiated and activated

### 4.1 Definition [P] https://ucp.dev/2026-08-25/specification/overview/ and https://ucp.dev/documentation/schema-authoring/
- Name: "All capability and service names **MUST** use the format: `{reverse-domain}.{service}.{capability}`". "The `dev.ucp.*` namespace is reserved for capabilities sanctioned by the UCP governing body. Vendors **MUST** use their own reverse-domain namespace for custom capabilities."
- Kinds: "Extensions can be: **Official**: `dev.ucp.shopping.fulfillment` extends `dev.ucp.shopping.checkout`; **Vendor**: `com.example.installments` extends `dev.ucp.shopping.checkout`".
- Schema: "A capability **MUST** declare a `schema`". "Extensions **MUST** be self-describing. Each extension schema **MUST** declare the types it introduces and how it modifies base types using `allOf` composition." The `$defs` key "**MUST** match the parent's full capability name exactly". Embedded top-level `name` and `version` (`YYYY-MM-DD`). Optional `requires: {protocol: {min, max}, capabilities: {...}}`.
- Versioning: "Third-party extensions and payment handlers publish versions on their authors' own schedules. Their versions remain independent of the selected `ucp.version`". Authoring guide example: `{"name": "com.shopify.loyalty", "version": "2025-09-01", "spec": "https://shopify.dev/ucp/loyalty", "schema": "https://shopify.dev/ucp/schemas/loyalty.json"}`.
- Forbidden: "Only UCP core defines members inside `ucp`, and extension authors **MUST NOT** place extension data there." An `allOf` extension can only add constraints, never widen a closed enum.

### 4.2 Publication [P]
- Authority binding: "a declared `schema` URL's origin **MUST** match the namespace authority in its name." So `com.offerad.*` must serve its schema from `offerad.com` (or the domain OfferAd actually owns). The platform "**MUST NOT** follow redirects (`3xx`) when fetching a `schema` URL"; shared CDNs and unrelated subdomains are rejected; "declare entities only under a **registrable domain** ... that you exclusively control."
- "This binding guarantees **provenance, not trust** ... Whether to negotiate, trust, or implement it is always the client's decision".
- The vendor capability is then listed in the Business profile (`/.well-known/ucp`) AND in the Platform profile, each with `version`, `spec`, `schema`, optional `extends`, optional `config`.

### 4.3 Negotiation and activation [P]
- "Businesses publish their profile at `/.well-known/ucp`; platforms publish their profile at the URI advertised in `UCP-Agent`." "Platforms **MUST** communicate their profile URI with each request". "This design enables **permissionless onboarding** — any platform with a discoverable profile can interact with any business without prior registration."
- Intersection: "**Compute intersection**: For each business capability, include it in the result if a platform capability with the same `name` exists." Exact version match. "**Prune orphaned extensions**". A third-party extension "advertises exact extension versions in Business and Platform profiles and is negotiated by exact-version intersection like every capability".
- Shopify's description [P] https://shopify.dev/docs/agents/profiles : "Negotiation is server-selects. The business computes the intersection of its capabilities with the platform's and chooses the active set". And, important for idea A: "A platform (an agent) declares only the checkout capability, with no extensions (for example fulfillment, discount, or buyer consent). The business intersects and returns checkout alone. Negotiation succeeds, but tools won't include fulfillment or discount input fields in their schemas." So on Shopify even `discounts.codes` over MCP exists only when the buyer platform's profile declares the Discount extension.
- Escape hatch: "Platforms and businesses **MAY** coordinate on pre-release implementations outside of public discovery."

### 4.4 Actions [P] overview "Actions"; schema authoring "Extension-Declared Action Types"
- "An Action is an outstanding unit of extension-defined work for a Platform to process ... Actions appear only in responses, under the `actions` map." "Cart, Checkout, and Catalog adopt this shape". "Each Action key is a reverse-domain **Action type**"; instance fields `id`, `config`.
- "A Business **MUST** emit an Action type only when an extension that declares it is active for the containing capability in the negotiated intersection."
- "The common Actions contract defines no generic machinery: no URL scheme, origin, or delegate policy ... no callback, result, state, polling, or executor." Each extension must define its own processing, completion and fallback.
- "Every Action type is declared by an extension and becomes available only when that extension is negotiated ... Negotiation is pre-runtime agreement on that contract's semantics and support; it does not pre-approve every future `config` value or delegate."
- Spec example: Action `com.example.identity.student_verification` with `config.verification_url`, paired with info message `eligibility_accepted`. This is the spec's own picture of "claim, then prove through a vendor Action".
- TC minutes 2026-07-10 [P]: "Actions Negotiation and Discovery (PR #553) ... actions should not bypass the negotiation process".

### 4.5 Request constraints and "Locked negotiated discount codes" [P] overview "Request Constraints"
- "In an authoritative response, a Business can use `ucp.request_constraints` to signal additional rules it will apply when evaluating request data in the next Platform request."
- The example titled "**Locked negotiated discount codes**": a checkout response (Discount extension active; line item "Bulk screws", quantity 24 at 1200) carries `"request_constraints": {"required": ["discounts"], "properties": {"discounts": {"required": ["codes"], "properties": {"codes": {"const": ["ACME-X7Q9-L2M4"]}}}}}` and `"discounts": {"codes": ["ACME-X7Q9-L2M4"]}`. "The next Checkout Update request is valid only if it satisfies the resolved request schema, contains `discounts.codes`, and supplies exactly `[\"ACME-X7Q9-L2M4\"]`."
- Origin: PR #655 by Ilya Grigorik (Shopify), merged 2026-08-20, https://github.com/Universal-Commerce-Protocol/ucp/pull/655 : "a Platform learns that a negotiated quantity is fixed or an otherwise optional field is required only after submission fails"; "Use `request_constraints` for rules known in advance (e.g., fixed purchase lot quantities, locked discount codes, or required billing fields)."
- What it implies about negotiated prices [I]: (a) the spec authors assume prices get negotiated, but outside UCP; (b) the carrier of the result is an opaque, business-issued discount code; (c) the only thing UCP adds is that the Business can pin that code so the agent cannot drop or swap it; (d) there is no field for who negotiated, why, or what was conceded. The Quote proposal #929 says the same thing from the other side: "Encode the result as a discount code | Today's workaround. No discovery, no lifecycle, no expiry semantics, the negotiated price appears as just another promotion in `discounts.applied`, and the agent is usually out of session when the code arrives." [P] https://github.com/Universal-Commerce-Protocol/ucp/issues/929
- Only the Business (on Shopify: Shopify itself) can emit `request_constraints`. An app cannot.

## 5. Item (4): what A2A and the Embedded Checkout Protocol allow that MCP does not

MCP binding [P] https://ucp.dev/2026-08-25/specification/shopping/checkout/mcp/ : typed tools only; "Business outcomes (including errors like unavailable merchandise) are returned as JSON-RPC `result` with `structuredContent` containing the UCP envelope and `messages`". No free-form turn, no server-initiated event, no delegation. The only free text is inside the fields of sections 2 and 3.

A2A binding [P] https://ucp.dev/2026-08-25/specification/shopping/checkout/a2a/ (specified for Checkout only):
- Free-form input: "Agentic applications can accept natural language input from users interacting with the agent to identify the user's intent, negotiate with the user to capture any required information and then invoke the appropriate tools to perform the operation. Inputs from platforms can be sent to the remote business agent as an A2A `Message`." Listed request formats include "Natural language input".
- Multi-turn state: section "Agent2Agent Negotiation": "Platforms must pass the business agent generated `contextId` for subsequent turns in a session"; "Platforms must be capable of handling further negotiation in the same session even after a task reaches a terminal state".
- Asynchronous work: "Business agents may also leverage A2A `Task` objects".
- The checkout still comes back as structured data: "The checkout object **MUST** be returned as part of a `DataPart`" under `a2a.ucp.checkout`.
- Discovery: "Businesses that support A2A transport must specify the agent card endpoint as part of `services` in UCP Profile"; agent card extension URI `https://ucp.dev/2026-08-25/specification/reference`; header `X-A2A-Extensions`.
- "Negotiation" in this page means dialogue to collect information, not price. But it is the one binding where a seller agent could answer a free-text "can you beat this?" inside the protocol. [I]

Embedded protocol [P]:
- Bidirectional JSON-RPC 2.0 over postMessage / MessageChannel between the business's own checkout UI and the host.
- Business-to-host notifications on every state change (`ec.line_items.change`, `ec.totals.change`, `ec.messages.change`, `ec.buyer.change`, `ec.payment.change`, `ec.fulfillment.change`).
- Delegation: the business UI asks the host to do work (`ec.payment.credential_request`, `ec.payment.instruments_change_request`, `ec.fulfillment.address_change_request`, `ec.window.open_request`), negotiated per session with `ec_delegate`.
- A human is in the loop: "The checkout has to be finalized manually by the user through a trusted UI unless the AP2 Mandates extension is supported."
- Extension messages allowed (`ec.{domain}.change`, `ec.{domain}.{action}_request`), again only for negotiated extensions.
- What it does NOT have: any host-to-checkout message carrying a discount code, an offer, or text.

Shopify today [L]: `mcp` + `embedded` only. No `a2a`, no `rest`.

## 7. Item (6): AP2 mandates

- AP2 v0.2 does not use the term "intent mandate" anywhere in the pages saved (searched all 15 saved AP2 files). [P] https://ap2-protocol.org/ap2/specification/
- "AP2 defines two Mandate types: Checkout Mandate and Payment Mandate". Each is open (`mandate.checkout.open.1`, `mandate.payment.open.1`, carrying constraints, used when the human is not present) or closed.
- Checkout Mandate constraints: `checkout.allowed_merchants`, `checkout.line_items` (acceptable items, quantity). Checked by the Merchant. [P] https://ap2-protocol.org/ap2/checkout_mandate/
- Payment Mandate constraints: `payment.amount_range` (min/max), `payment.budget`, `payment.agent_recurrence`, `payment.allowed_payees`, `payment.allowed_payment_instruments`, `payment.allowed_pisps`, `payment.reference`, `payment.execution_date`. Checked by the Credential Provider, Network or payment processor, not the merchant. [P] https://ap2-protocol.org/ap2/payment_mandate/
- Disclosure rule: "Verifiers of Mandates *always* receive a closed Payment and Checkout Mandate"; "Only constraints relevant to the closed Mandates are shared with the verifier."; "Shopping Agents MUST present only the disclosures from the open Mandates needed in the evaluation of the closed Mandates."
- So: a seller sees which items and which merchants were authorized, at completion time. The seller does not see the buyer's price cap or budget, and receives nothing before the decision. An open mandate is an authorization boundary for the agent, not a request for offers. [I]
- The merchant's one lever: "A Human Not Present flow can be turned into a Human Present flow by the Merchant (or Credential Provider) returning an `unresolved_constraint` error and bringing the User back into the loop". [P] https://ap2-protocol.org/ap2/flows/
- AP2 does expect offers to arrive through the shopping integration, not through mandates: "This may include the ability for the merchant to provide loyalty, offers, cross-sell and up-sell information (*via the integration between the Shopping Agent & Merchant*) which the Shopping Agent should represent to the user". Canonical scenario: "buy these shoes for me when the price drops below $100". [P] https://ap2-protocol.org/overview/
- Extension point: a new constraint needs a unique `type`, a schema and an evaluation algorithm. A future `checkout.*` constraint type is where a seller-answerable condition could live. [P][I]
- In UCP: `ap2.merchant_authorization` (detached JWS over the checkout), `ap2.checkout_mandate`, payment mandate in the instrument token; no open-mandate field. [P] A changed total (for example a late discount) no longer matches the checkout the mandate embeds, so a new mandate is needed; this is stated in proposal #929 ("an AP2 `checkout_mandate` no longer matches the Checkout it embeds ... so a new mandate is required before completion"), not tested. [S] Shopify does not advertise the AP2 extension on Allbirds. [L]

## 9. Workaround ideas: A to F reassessed, and new ones

### A. Offer token = single-use discount code + link. KEEP; it is the spec's own model.
- Evidence: 4.5 (spec example), #929 ("Today's workaround"), I Want That's live response shape in #502.
- Improve: (1) return TWO links, the UCP permalink `https://{store}/buy/{items}?discounts/codes/0=CODE&attribution/utm_source=offerad` when the store advertises `dev.ucp.shopping.permalink`, and the legacy `/cart/{variant}:{qty}?discount=CODE`; (2) return the bare code too, for agents that hold a UCP session and whose profile declares the Discount extension; (3) put the concession label in the discount title, because `applied[].title` and the `discount` total line are what a conformant platform shows.
- Honest limits: the agent must already be talking to the OfferAd endpoint; "Permalinks MUST NOT contain ... one-time secrets", and a single-use code in a URL sits close to that line, so make the code bound to the cart contents and short-lived rather than a bearer secret; over MCP the `discounts` input disappears if the agent's profile lacks the Discount extension; Shopify tells agents "Only prompt if customer mentions having a discount code"; the agreed price shows up as "just another promotion"; with AP2 a late price change needs a new mandate.

### B. Discovery. PARTLY ALIVE; the spec explains exactly why it is weak.
- Any text placed in B1 to B10 is data, not an instruction (section 2, hard limits). So the target of discovery text is the HUMAN, through what the agent must or will render, plus a link.
- Channels an app can plausibly feed on Shopify, strongest first: discount title in `discounts.applied[]` (after a cart exists); a rejection message for an entered code (see C); product description, tags and collection description in catalog output; shipping option names in `fulfillment`; policy pages behind `links[]`; FAQ/policy text behind Shopify's FAQ tool and, later, `ask_business`.
- B(i), an app-registered WebMCP tool, is outside UCP: UCP 2026-08-25 has no WebMCP binding (a draft is in progress), so page tools are not subject to profile intersection [I]. That is a real crack, limited to browser agents.
- B(v), the cross-store connector, is the only variant where the agent was told about the tool. UCP supports it: "permissionless onboarding — any platform with a discoverable profile can interact with any business without prior registration". The connector can itself be a UCP Platform with its own hosted profile.

### C. Offer menu carried by codes. KEEP and SHARPEN: "codes as the agent's voice".
- In UCP terms `discounts.codes` is the one agent-to-business field that is an opaque string list, reaches app code on Shopify (Discount Functions see entered codes, per R1), and has a defined answer channel: `applied[].title` on success, a must-display warning on rejection.
- So a code is a question ("OFFERAD-SPEED", "OFFERAD-MATCH-<token>") and the title or the rejection text is the answer. Shopify's Discount Function API allows "apps to conditionally reject discount codes with a custom message" (R1 notes; https://shopify.dev/changelog/posts/discount-rejection-support-for-discount-functions).
- Depends on a live test on OUR OWN dev store: does the function's custom rejection message arrive in UCP `messages[].content`, and the candidate message in `applied[].title`?
- Limits: one round per update; the agent must know the code vocabulary (again discovery); codes are not secret.

### D. `context.eligibility`. Spec-perfect, closed on Shopify today.
- The spec describes exactly this: reverse-domain claim, provisional discount, verification "by an Action surfaced by a negotiated extension, or any other mechanism". A claim like `com.offerad.competing_offer` is legal.
- On Shopify the field is accepted but apps cannot read it (brief item 7), and "Businesses MUST ignore unrecognized values without error". Values "MUST be non-identifying", so a competing-offer URL does not belong there.
- Viable on a UCP server OfferAd controls, and worth asking Shopify to expose to Functions.

### E. Custom UCP extension `com.offerad.*`. Mechanics clear; blocked on Shopify; viable elsewhere.
- Two blockers: Shopify's profile is not app-extensible, and no buyer platform lists `com.offerad.*`. Activation needs both.
- Better shape than "extension with Actions": a ROOT vendor capability with `config.endpoint`, copied from `com.shopware.quote`. It needs no change to cart or checkout responses; the platform reads the profile and calls the vendor endpoint. Result comes back as a code or, later, a quote id.
- Requirements: schema on a domain OfferAd exclusively controls matching the namespace, no redirects, exact version string in both profiles.
- This is also the governance-approved first step ("first be self-hosted under a vendor namespace ... and proposed for adoption").

### F. Draft orders / invoice URLs. Outside UCP; equivalent to `continue_url` or a permalink handoff. The human finishes. No spec conflict.

### New G. Ride the standards train (Offer #738/#773, Quote #929, approaching/available discounts #482/#609).
- OfferAd's "labeled concession with seller limits in code" is the missing business-side engine for all three. Shopify shipped 2026-08-25 within about ten days, so a December release could reach every store early in 2027.
- If `discounts.available[]` (#609) ships, a code-type promotion's existence and conditions are shown to every agent without revealing the code: a built-in discovery channel for A and C.
- Limit: the Offer proposal excludes "a new discount model" and has no counter-offer; the Quote proposal is price-only and one round; neither gives a third-party app a hook on Shopify. The owner would have to decide to engage (we did not post anything).

### New H. Competing-offer proof as a signed attestation.
- UCP `signals` explicitly allows "cryptographically signed results from an external verifier that the business can validate against the provider's published key set" under a reverse-domain key. OfferAd can be that verifier: it fetches the competing link itself, signs `{competitor, item, price, seen_at}`, and the agent relays it as `com.offerad.competing_offer`.
- On Shopify, `signals` is not on cart or checkout, so the attestation goes to OfferAd's endpoint and comes back as a code. The shape still matters: it is the form the council already accepts (#534/#535), and it answers the "verify it itself" requirement without trusting the agent.

### New I. `ask_business` as the question channel (draft; Shopify listed it first in its backlog).
- "Do you match prices?" gets a business-authored `answer` plus `links[]` plus an info message whose example code is `promotion`. The answer cannot apply anything ("`ask` answers; it does not act"), but it can hand over a link, and that link can be the OfferAd offer link.
- Depends on Shopify shipping ask and on what content feeds its answers (policies, FAQ, knowledge base). Platforms SHOULD show the answer "as content from the Business".

### New J. `policies[]` with a custom type.
- The only core, un-negotiated, structured statement a business can make, and the spec's example is a price-match policy. `{"type": "com.offerad.policy.price_match", "description": ..., "url": ...}` is exactly on-spec.
- Shopify does not emit `policies[]` today. Viable on other UCP businesses now; on Shopify only if Shopify maps shop policies or app data into it.

### New K. The embedded checkout moment.
- When the agent host embeds the checkout, the store's own checkout UI runs and reports `ec.totals.change` / `ec.line_items.change` / `ec.messages.change` to the host. An offer shown and applied inside that UI is seen by the agent through standard messages, with a human present.
- Depends on Shopify checkout extensibility (plan limits are in R1) and on agent hosts using the embedded transport.

### New L. A2A seller agent on OfferAd's own domain.
- The only UCP binding with free-form text both ways and multi-turn context. A real "arena" endpoint can be a UCP-over-A2A business agent with an agent card. Shopify will not host it; discovery is again the open problem.

### New M. Attribution as the measurement loop.
- `attribution` (and permalink `attribution/*`) reaches Shopify today and is "Forwarded to the cart for downstream reporting". Tag every OfferAd offer (`utm_source=offerad`, `activity_id_value=<offer id>`). It can never trigger a discount ("MUST NOT affect the response").

## 10. Corrections to the brief

1. Item 2: the Allbirds profile also advertises `dev.ucp.shopping.permalink` (`https://www.allbirds.com/buy`) and only two transports, `mcp` and `embedded`. No A2A, no REST.

3. Item 5: correct for the released spec, but the spec's own example is named "Locked negotiated discount codes"; and an Offer extension (#738/#773, December milestone), a Quote extension with a buyer price proposal (#929/#930, 11 Oct 2026) and approaching/available discounts (#482/#609) are in flight. `ask` is merged into `draft` (PR #538), tool name `ask_business`, with `links[]` and an info code example `promotion`.
