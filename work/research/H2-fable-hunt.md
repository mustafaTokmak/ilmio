## 0. Executive summary (one screen)

1. The brief's picture of the Shopify side is right and I confirmed it against the live 13-tool schema: the only agent-controlled inputs that reach an app's Discount Function are line items, `buyer.email`/`phone`, and `discounts.codes`. `context.intent`, `context.eligibility`, `attribution` and `signals` do not appear among Discount Function inputs (`primary_source_read`, see §1.13). There is no cart-attributes field in Cart/Checkout MCP (`tested_live`, §1.2).
2. Three things the brief missed, all primary-source and two of them tested live:
   - **Every Shopify store serves `/agents.md` (mirrored at `/llms.txt` and `/llms-full.txt`), a Shopify-written "Agent Instructions" document that tells agents how to shop the store, and a merchant can replace it with a theme template `agents.md.liquid`** (§1.1). This is the sanctioned place to tell agents about an offer desk. It is store-level, not app-level, so the app has to ask the merchant to add a one-file template (or do it with the merchant's theme-edit permission).
   - **Shopify's "direct checkout" inside Meta (Muse), Microsoft Copilot and (per Shopify) Google surfaces runs Shopify Functions and accepts discount codes, but renders no checkout blocks, no pixels, no theme code** (§1.3). So in the channel that matters most for Muse, the app's only levers are Catalog text, codes, and Functions.
   - **Muse has a third-party connector platform (MCP, reviewed, tools classed Read / Write / Sensitive write) with explicit rules against fabricated discounts and undisclosed commercial influence** (§1.4). A cross-store OfferAd connector is therefore a real, policy-shaped route into Muse, not just into Grok/ChatGPT/Claude.
3. Agent-side reality (§2): the acting agents (Muse, Dots, Grok Bot) run in their own cloud browsers, prefer connectors when the user has installed one, and otherwise operate pages like a human. None of their makers' pages say they implement WebMCP; Chrome says WebMCP agent support is extension-based, in an origin trial, "primarily designed for local browser workflows with a human in the loop" (§1.8). All of them gate purchases behind user approval and treat page content as untrusted. The offer must therefore (a) be legible as a *benefit to the user* on the page or in a connector result, not as an instruction, and (b) end in a discount code or a URL the agent can submit through a documented field.
4. The universal "applies in checkout" sink is a **discount code** (UCP `discounts.codes`, Checkout WebMCP `update_checkout.discounts.codes`, permalink `?discount=`, the code field in every Shopify checkout including Meta/Copilot direct checkout). A Discount Function lets one code carry product, order and shipping effects on any plan. A free gift, extended returns, delivery guarantee and next-order credit ride on the same code as a *signed promise* the app fulfils post-purchase (order tag → app action).
5. Twelve mechanisms are designed in §3. **Build first: M1 "Offer Desk on the store domain" (app-proxy MCP endpoint + one single-use app code discount per accepted offer + one Discount Function), shipped together with M3's public priority menu as the zero-tool fallback and with discovery text in the three channels Shopify itself feeds to agents (product description → Shopify Catalog, `agents.md`, FAQ/policies).** The same backend later serves M2 (buyer-installed connector), which is the route most likely to be *used* by Muse/Grok/ChatGPT, but which cannot be tested without a listing or a user-added custom connector. The first cheap test is a one-day probe of whether any agent calls the desk unprompted (§4).

The app can provide the exact file text and a deep link to the theme code editor. Replacing the Shopify default means the app must re-render the default sections (using the `agents` object) and append its own section, and must keep up with Shopify's default as it evolves. `secondary_source` (Shopify community thread via search): the fallback chain shipped on 28 May 2026; Google has said it ignores llms.txt for Search.

### 1.8 WebMCP — can an app register an extra tool on a Shopify storefront?

- https://developer.chrome.com/docs/ai/webmcp (`primary_source_read`): access gated by a `tools` Permissions Policy which "defaults to `self`, which allows tool registration in top-level and same-origin contexts"; origin trial "from Chrome 149"; "primarily designed for local browser workflows with a human in the loop"; agents named are Chrome extensions ("Example Agentic Chrome Extension", "Model Context Tool Inspector Extension"); "These extensions are separate from Gemini in Chrome."

- Shopify WebMCP docs (saved `web-mcp.md`, `primary_source_read`): "Shopify provides WebMCP tools on every Liquid storefront"; "agent support for WebMCP is currently limited to Chromium-based browsers"; storefront tools: `search_catalog`, `browse_store`, `get_product`, `show_variant`, `get_cart`, `update_cart`, `cancel_cart`, `proceed_to_checkout`, `manage_orders`, `search_shop_policies_and_faqs`. Checkout: "The tools also don't cover app-defined checkout extension interactions" (saved `carts-checkout.md`).
- `inferred`: a theme app embed script runs in the storefront document's origin, so by the Chrome policy it *can* call `registerTool` on the same document and an agent's `getTools()` would list it next to Shopify's. Shopify publishes no rule for or against this; it is the kind of thing a platform may later block. Cheap to test on a dev store with `chrome://flags/#enable-webmcp-testing` and the Tool Inspector extension. No evidence that Muse, Dots or Grok Bot consume WebMCP at all.

## 2. Part 1 — What each buyer agent actually sees, and when an offer can enter

Shared facts: every acting agent gates purchases behind user approval (Muse "will always ask"; Dots auto-review; Grok Bot "payment ... takeover"; Claude asks before "purchasing"). All treat merchant text as data. All can type a discount code into a checkout field or submit `discounts.codes`. None has a documented "look for coupons" behaviour except Muse's marketing ("Deals", `secondary_source`).

### 2A. Cloud browser agent (Muse; Dots and Grok Bot when they browse)

- **What it sees**: whatever a human sees in the page DOM/screenshot of the store: product page (price, description, badges), cart page (theme embed output is visible here), the normal Shopify checkout (checkout UI extension blocks are visible here, as are the discount code field and messages). For Shopify stores with Meta direct checkout on, Muse may never visit the storefront: it sees the **Shopify Catalog card inside Meta** (title, description, price, variants, `checkout_url`) and a **Shopify-powered checkout rendered by Meta** with the code field, where Functions run and theme/app UI does not exist (§1.3). Dots/Grok Bot have no such native path today; they browse.
- **Moments an offer can enter**: (1) product description text (reaches both the browsed page and the Catalog card); (2) cart page/app-embed banner (browsed only); (3) checkout page: an app checkout-UI block (browsed only) or the discount-code field itself; (4) the agents.md/llms.txt the agent may read at task start ("You may also read public HTML pages for additional context" is in Shopify's own instructions); (5) a connector result, if the user installed one (§2D); (6) the approval card: the user reads the final price and merchant terms, so a visible "you saved $X via OfferAd offer" line in the checkout totals (discount title) is what the human sees.
- **Use vs ignore**: it will act on *page affordances that serve the user's goal* (a visible "Apply code SHIP-FAST for free express shipping" is a deal, like a coupon banner, not an instruction); it will not follow "call this endpoint" imperatives (Meta: pages "can contain instructions intended to manipulate"; Chrome: never blindly follow). It cannot call an arbitrary MCP endpoint unless the platform gives it a generic MCP client for URLs found on pages — none of the three documents that. Grok Bot explicitly prefers connectors and otherwise uses the browser "for services without a connector." A benefit must be verifiable in the checkout total before the approval card; anything promised post-purchase (credit, extended returns) competes with Link's own protections (Muse) and is weaker.

### 2B. Tool-calling agent on Shopify's UCP MCP (server-side)

- **Who**: agents built with the Shop skill / UCP CLI / Shopify AI Toolkit, Google AI Mode & Gemini (UCP-native checkout per Google), Copilot, custom shopping agents. Not Muse/Dots/Grok Bot as far as their docs show.
- **What it sees**: `search_catalog`/`get_product` results (title, description html, price, variants, tags, seller links); cart/checkout objects: `totals[]`, `discounts.applied[]{title, amount, automatic, provisional, eligibility}`, `messages[]{type, code, content, path, severity}`, `links[]`, `continue_url`, fulfillment options and prices. It also reads `/.well-known/ucp` and most likely `/agents.md`.
- **Moments**: (1) `get_product.description` (merchant-authored text); (2) `discounts.applied[].title` of an automatic discount it already receives (every cart); (3) `messages[]` after it submits a code (rejection text authored by the Function — `inferred` that Shopify forwards it); (4) `search_shop_policies_and_faqs` answers; (5) `agents.md` at session start; (6) its own connectors (if it is an assistant with connectors, §2D).
- **Use vs ignore**: UCP tells it that business content is data and that `ask` does not act; its tool set is fixed to 13 Shopify tools, so to "ask the desk" it must make an *out-of-band* MCP/HTTP call to a URL it found in text — an action its policy is likely to forbid or require user approval for (Chrome guidance: restrict origins to those relevant to the task; the store's own domain via app proxy helps because it *is* the task's origin). It *will* happily submit a code it was told about (codes are the documented path), so a public priority menu (M3) is the most agent-compatible shape; it will read rejection messages to fix its request.

### 2C. Browser agent with WebMCP (Chromium extension-based)

- **Who**: Chrome extensions in the origin trial; "Example Agentic Chrome Extension"; possibly future Gemini-in-Chrome (not stated). Not Muse/Dots/Grok Bot (no evidence).
- **What it sees**: `getTools()` on each page: Shopify's storefront tools, and on checkout the 4 checkout tools; tool results (structured JSON) including `discounts.applied`, `messages`; page text if it also reads the DOM.
- **Moments**: (1) an *extra WebMCP tool registered by the app embed* on storefront pages (`com.offerad.get_offer` with `readOnlyHint`) — appears in the same `getTools()` list as Shopify's; (2) `search_shop_policies_and_faqs` results; (3) checkout `update_checkout.discounts.codes` (sink); (4) agents.md.
- **Use vs ignore**: Chrome guidance makes it treat tool definitions as untrusted and to confirm consequential actions; a read-only tool that returns a code with a plainly better total is low-risk and benefits the user, so it is plausible it calls it. But this population is tiny today and Shopify's own instructions say "Agents must use the provided WebMCP tools for all agent-initiated shopping actions" — an app tool that *returns a code* (no state change) stays inside that rule; a tool that mutates the cart would not.

### 2D. Assistant with user-installed connectors (Grok custom connector, ChatGPT plugins/apps, Claude connectors, Muse connectors)

- **What it sees**: its connector's tool list and results, plus whatever shopping path it uses (browser or UCP). Grok: "Grok can use the connector's tools automatically whenever your questions relate to that service." Muse: approved connectors are "discoverable by the Muse agent"; Read tools ask "On first use ... unless Always allow". Dots: "Each plugin must be connected and permitted".
- **Moments**: whenever the user's task is "buy X" and the connector's description says it finds better conditional offers at participating stores — the agent can call `find_offers(store_url, product_url, priority, competing_url)` *before* checkout and then submit the returned code. The trust problem inverts: the user chose the tool; the store never has to be trusted to issue instructions.
- **Use vs ignore**: it uses the connector when its description matches the task and when it does not contradict platform rules (Muse: no fabricated discounts, disclose commercial relationships, don't steer from competitors). It ignores it if the connector tries to be a sales channel for one merchant without disclosure. Cross-store, buyer-side framing ("get the best conditional offer from any participating store") fits every platform's rules I read.

### 2E. Catalog-fed native checkout (Meta direct checkout, Copilot, Google UCP checkout)

- Added because it is where Muse's Shopify purchases are designed to land. The agent/platform sees Shopify Catalog data and runs a Shopify checkout it renders itself: **codes and automatic discounts supported, Functions run, no checkout blocks, no pixels** (§1.3). Offer entry: Catalog description text and a code the user or agent already knows (from a connector or the description). Nothing else.

## 3. Part 2 — Mechanisms (12 designed, 2 rejected)

Template per mechanism: steps → agent-side requirement → Shopify-side requirement → discovery → proof verification → abuse limits → non-discount offers → multi-round → cheap test → confidence (0–1 that it can work end-to-end *today* for at least one real agent population) → unverified assumptions.

Common components referenced below:
- **DF** = one app Discount Function (classes ORDER, PRODUCT, SHIPPING) deployed by the app; reads `discount.metafield` config, `cart.attribute`, line attributes, `buyerIdentity`, `enteredDiscountCodes`, `triggeringDiscountCode`; emits product/order/shipping candidates with a `message` (the title agents see) and rejection messages.
- **Offer token** = a signed JSON (variant ids, concession type + value, floor already applied, expiry ≤ 30–60 min, buyer email hash or none, offer id, merchant id, HMAC with a per-merchant key stored in the discount metafield / app).
- **Code sink** = a Shopify discount code the agent submits; universal across UCP MCP, Checkout WebMCP, browser checkouts, Meta/Copilot direct checkout, permalinks.
- **Verifier** = M6, the competing-offer URL check.

### M1. Offer Desk on the store's own domain (app proxy MCP) → single-use offer code → DF

- **Steps**: (1) Agent reads the offer-desk pointer (see discovery) and calls `POST https://{store}/apps/offerad/mcp` (JSON-RPC MCP via app proxy; also plain `GET /apps/offerad/offer?variant=…&priority=…&proof=…` for non-MCP agents). Tools: `get_offer_options(variant_id)` (read-only: lists concession types the merchant allows, no amounts), `request_offer(variant_id, quantity, priority: price|speed|returns|bundle|credit, competing_url?, buyer_email?, agent_profile?)`. (2) Desk runs the Verifier on `competing_url` if given, applies merchant limits in code (floor, budget, allowed concessions, per-buyer caps), decides a concession. (3) Desk calls Admin `discountCodeAppCreate` for *this offer*: `code = OA-<10 chars>`, `functionId`, `usageLimit: 1`, `appliesOncePerCustomer: true`, `startsAt: now`, `endsAt: now+45m`, `combinesWith` per merchant, `metafields[{namespace:"$app", key:"offer", value: <offer token JSON>}]`, optional `context.customers` when `buyer_email` is known and a customer record exists. (4) Desk returns `{code, expires_at, offer: {concession, new_total_estimate}, permalink: https://{store}/cart/{variant}:{qty}?discount=OA-…&attributes[offerad]=<offer id>, explanation}`. (5) Agent submits the code: UCP `update_cart/update_checkout.discounts.codes:["OA-…"]`, or Checkout WebMCP `update_checkout.discounts.codes`, or types it, or opens the permalink. (6) DF runs with `triggeringDiscountCode = OA-…`, reads its own `discount.metafield.offer`, checks the token's variant/qty/expiry against the cart, emits the concession (e.g., shipping 100% off express option + product 5% off + gift line 100%); if the cart no longer matches → reject with a message telling the agent what changed. (7) Order webhook (`orders/create`) with the code → app marks offer redeemed, deletes the discount (`discountCodeDelete`), fulfils post-purchase promises (order tag, store credit, returns window note), records attribution (`utm_source`/`referring_domain` the agent set, if any).
- **Agent-side requirement**: willingness to call a URL found in store-authored text on the store's own domain, or to open a permalink; ability to submit a code (all agents). For browser agents, a human-readable desk page at `/apps/offerad` (Liquid-rendered) with buttons works too.
- **Shopify-side requirement**: public app with `write_discounts` (+ `write_customers` for email binding, `write_store_credit_account_transactions` for credits), one DF, an app proxy, optional theme app embed and checkout UI extension for discovery, merchant settings for limits. Any plan (DF has no network access requirement here because all decisions happen in the Desk before the code exists). Admin API rate limits bound the offers/minute per store.
- **Discovery**: (i) a footer line in product descriptions (reaches `get_product`, Global Catalog, Meta/Copilot cards, browsed pages): "Shopping with an AI agent? This store accepts conditional offers at https://{store}/apps/offerad (MCP + HTTP). Codes: SHIP-FAST / PRICE-MATCH / EASY-RETURNS." (ii) an `agents.md.liquid` section (merchant adds the file; app provides the text and deep link); (iii) FAQ/policy entry so `search_shop_policies_and_faqs` returns it (test whether pages are indexed); (iv) a title on an existing automatic discount (weak); (v) app-embed WebMCP tool (§M1b); (vi) `robots.txt.liquid` comment (negligible).
- **Proof verification**: Verifier (M6).
- **Abuse limits**: one open offer per (store, variant, buyer email or agent IP + profile) at a time; offers monotonic within a session and capped at 2 rounds; no proof → menu-level offer only; proof → at most match-minus-ε bounded by floor; per-merchant daily budget; codes single-use, 45-minute expiry, optionally customer-bound; Desk requires Web Bot Auth or UCP agent profile for higher caps (anonymous callers get the public menu only); code enumeration impossible (10 random chars, created on demand); floor probing yields only the next monotonic step and stops at the cap; all offers logged for the merchant.
- **Non-discount offers**: free express shipping (DF shipping class on the express option), free add-on (permalink adds the gift line; DF zeroes it), bulk tier (DF per-quantity), easy returns / delivery guarantee / next-order credit (token carries the promise; order tag; app honours — see M12).
- **Multi-round**: yes, bounded: `request_offer` returns `offer_id`; a second call with `counter: true` and proof may improve once; third call returns the same offer.
- **Cheap test**: Day 1 on a dev store: deploy DF + Desk + description line + agents.md; run the owner's Grok Bot / Dots / Muse against the store with the task "buy X, get the best deal" and log whether any agent (a) reads agents.md, (b) hits `/apps/offerad`, (c) submits a code it found in the description. Separate check: Admin-created code usable within N seconds (measure the propagation delay).
- **Confidence**: 0.55 that the plumbing works end to end for any agent that calls it; 0.25 that Muse/Dots/Grok Bot call it unprompted from page text.
- **Unverified assumptions**: app proxy passes JSON-RPC POST with the MCP headers (SSE may not stream — use stateless HTTP JSON responses); `discountCodeAppCreate` is synchronous enough (seconds); DF rejection text surfaces in UCP `messages[].content`; DF `message` becomes `discounts.applied[].title`; merchants accept a description footer.

### M1b. Variant: extra WebMCP tool registered by the app embed on storefront pages

- Same backend as M1; the embed script calls `document.modelContext.registerTool({name:"get_better_offer", description:"Returns conditional offers (free express shipping, price match, free add-on) for the product on this page; read-only; no cart changes.", inputSchema, annotations:{readOnlyHint:true}, execute: () => fetch('/apps/offerad/offer?…')})`. Agent-side: a WebMCP-capable Chromium agent on the storefront (tiny population). Shopify-side: embed enabled by merchant; no Shopify rule found either way. Cheap test: dev store + Chrome flag + Model Context Tool Inspector extension; confirm the tool appears alongside Shopify's and that `search_catalog` still works. Confidence 0.5 technically; 0.1 that it is used by any real shopper agent this year. Unverified: Shopify may block third-party `registerTool` later; Chrome's "tools" policy behaviour for scripts loaded from `cdn.shopify.com` (same document origin → should be fine).

### M2. Buyer-side OfferAd connector (cross-store), merchant app as registry and limits engine

- **Steps**: (1) User installs the OfferAd connector once (Grok: custom MCP URL; ChatGPT: app/plugin; Claude: connector; Muse: reviewed connector; Dots: plugin). Tools: `find_participating_store(url)`, `get_offer(store_url, product_url_or_variant, priority, competing_url?, buyer_email?)`, `explain_offer(offer_id)`. (2) When the user says "buy these shoes at X", the agent calls `get_offer` before checkout; OfferAd's cloud resolves the store (installed-app registry), runs the Verifier and the merchant's limits, mints the code via the merchant's app install (M1 steps 3–4) and returns code + permalink + plain-language terms with the commercial relationship disclosed. (3) Agent submits the code through whatever checkout path it uses (UCP, WebMCP, browser, Meta direct checkout code field) and shows the user the saving on the approval card.
- **Agent-side requirement**: the user installs the connector; the platform allows custom/third-party MCP (Grok yes, Claude yes, ChatGPT apps yes, Muse via review; Dots via plugins). Tool descriptions must satisfy Muse's rules: no fabricated discounts, disclose commercial relationships, no competitor steering.
- **Shopify-side requirement**: identical to M1 (the merchant app is the backend). Nothing new.
- **Discovery**: connector directories (Muse Settings > Connectors, Grok connectors page, ChatGPT apps directory, Claude connectors), plus the store-side pointers of M1 which can say "or use the OfferAd connector".
- **Proof verification**: Verifier (M6), run by OfferAd with the agent's identity known (platform OAuth), so proof abuse is attributable.
- **Abuse limits**: per-user rate limits (OAuth identity), per-store budgets, same code rules as M1; because the caller is identified, floor probing is traceable and can be throttled per user; code sharing is pointless (customer-bound codes when email known, single-use).
- **Non-discount offers**: same as M1; connector can also show "credit on your next order at this store" with a verifiable store-credit grant after purchase.
- **Multi-round**: yes, same bound; the agent can relay the user's preference ("I'd rather have faster shipping").
- **Cheap test**: add the Desk as a *custom MCP connector in the owner's own Grok account* (grok.com/connectors → Custom → URL), then ask Grok to buy a product at the dev store and watch whether it calls `get_offer` unprompted ("Grok can use the connector's tools automatically whenever your questions relate to that service") and whether it then submits the code. Repeat with Claude connectors. Muse requires submission/review — not a one-day test.
- **Confidence**: 0.7 that an installed connector is used and the code applies; 0.3 that enough users install it to matter (distribution problem, not a technical one).
- **Unverified assumptions**: Muse review accepts a cross-store deals connector (its rules are compatible; approval "not guaranteed"); Grok Bot (as opposed to Grok chat) exposes user-added custom connectors (docs say installed connectors are account-wide, "installed as plugins from Connect apps").

### M3. Public offer menu: priority-named codes, enforced by the DF, no negotiation

- **Steps**: merchant publishes 3–5 codes in the product description/agents.md/FAQ: `SHIP-FAST` (free express), `PRICE-5` (5% off, not on sale items), `EASY-RETURNS` (60-day returns, tagged), `BUNDLE-2` (second item 20% off), `CREDIT-10` ($10 next-order credit). Agent picks the one matching the user's priority and submits it; DF enforces conditions and rejects with a guiding message ("PRICE-5 can't combine with sale items; SHIP-FAST is available"). One app code discount per menu item (5 discounts, `usageLimit` unlimited, `appliesOncePerCustomer`).
- **Agent-side**: nothing beyond submitting a code — the most compatible shape with every agent and with Shopify's own instructions.
- **Shopify-side**: DF + 5 code discounts + description text. Any plan.
- **Discovery**: as M1 (description, agents.md, FAQ). Also exportable to Stripe/Google promotion feeds for merchants on those (M13).
- **Proof verification**: none (no proof concept) — unless `PRICE-MATCH` is a code that the DF only honours when a line attribute `offerad_proof=<verified id>` exists (that makes it M5).
- **Abuse limits**: public codes are public; limits live in DF conditions (min cart, product class, once per customer). Floor is published by construction — the honest limit: this is a menu, not a negotiation.
- **Non-discount offers**: shipping, returns, credit, bundle all expressible.
- **Multi-round**: none (the agent can try another code).
- **Cheap test**: 2 hours on a dev store; then test with each agent whether it picks the right code from the description for a stated priority.
- **Confidence**: 0.8 it works mechanically; it is the floor on which M1/M2 stand.
- **Unverified**: whether Meta's Catalog card shows the description footer in full.

### M4. Identity-keyed deal: negotiate once, no code — automatic app discount keyed on the buyer's email/customer record

- **Steps**: (1) Agent negotiates at the Desk (M1/M2) and gives `buyer_email` (it will set `buyer.email` on cart/checkout anyway — documented field). (2) Desk creates/finds the customer (`customerCreate`/`customerUpdate`) and writes a customer metafield `offerad.deal = <token>` (or tag `offerad:<offer id>`). (3) An *automatic* app discount (one of the 25) runs the DF on every cart; DF reads `buyerIdentity.customer.metafield("offerad","deal")`, verifies HMAC + expiry + variant match, applies the concession. (4) Agent sets `buyer.email` in `update_cart`/`create_checkout` (UCP) or the email field (browser); Shopify resolves the customer; discount shows in `discounts.applied` as automatic with the title. (5) Post-order: webhook clears the metafield.
- **Agent-side**: only `buyer.email` (already needed for checkout). Works in UCP MCP, browser, Meta direct checkout (automatic discounts supported there).
- **Shopify-side**: `write_customers`, metafield definition, one automatic app discount, DF.
- **Discovery**: as M1/M2 (the ask still happens at the Desk).
- **Proof**: Verifier at the Desk.
- **Abuse limits**: the deal is bound to an email that must receive the order; one active deal per email per store; floor probing limited by per-email caps and identity; code sharing impossible (no code).
- **Non-discount**: same as M1.
- **Multi-round**: at the Desk.
- **Cheap test**: on a dev store, create a customer with the metafield via Admin API, then as a *guest* run a UCP `create_cart` with `buyer.email` and check whether `buyerIdentity.customer` resolves in the DF input (log it) and the discount applies pre-login. Also check Meta/Copilot direct checkout later.
- **Confidence**: 0.5 (hinges on guest-email → customer resolution; Shopify help says segment customers "can be identified when they check out using a valid email address or phone number", which suggests yes, but new-customer timing caveats exist).
- **Unverified**: guest email resolution to `customer` in Function input; metafield freshness at checkout; privacy posture (creating customer records from agent-provided emails before purchase).

### M5. Signed offer token carried as a cart attribute / line property (no code, no identity)

- **Steps**: (1) Desk returns a permalink `https://{store}/cart/{variant}:{qty}?attributes[offerad]=<token>` (and/or `properties=<base64 {"_offerad":"<token>"}>` on the first line) plus a storefront URL `/products/{handle}?offerad=<token>`. (2) For storefront navigation, the app embed script reads `?offerad=` and writes the cart attribute via AJAX `/cart/update.js` (standard theme behaviour). (3) The automatic app discount's DF reads `cart.attribute(key:"offerad")`, verifies HMAC/expiry/variant, applies the concession; Cart Transform `lineExpand` (any plan) can turn the main line into "product + free gift" components when the line property is present. (4) Checkout keeps attributes; order carries them (visible in admin Notes).
- **Agent-side**: open a URL (all browser agents; UCP agents when they hand off via `continue_url`). Not available to pure Cart/Checkout MCP flows (no attributes field) — those use the code path.
- **Shopify-side**: embed enabled; DF; Cart Transform (optional). Any plan for `lineExpand`.
- **Discovery/proof/abuse**: as M1; token is unguessable and single-use (DF checks a per-token redemption flag? — the DF cannot write state, so single-use is enforced post-order by the app; expiry limits reuse window; the token binds variant and quantity so sharing only helps someone buying the same thing within minutes — acceptable or block via buyer-email hash in token).
- **Non-discount**: free gift via Cart Transform; shipping via DF.
- **Cheap test**: dev store, permalink with `attributes[offerad]=…`, confirm DF sees the attribute at cart and checkout (attribute persists through `/cart/c/<id>`?) and that Meta direct checkout is *not* reachable this way (it is not).
- **Confidence**: 0.6 for browser agents and hand-offs.
- **Unverified**: attribute persistence from permalink into checkout for guest carts; whether Shopify strips unknown attributes anywhere.

### M6. Competing-offer verification service (component used by M1, M2, M4, M5)

- **Steps**: (1) Normalise URL; reject non-https, IPs, URL shorteners, user-content hosts (Google Docs, Pastebin, social). (2) Fetch server-side with a declared bot UA from a fixed egress; follow ≤3 redirects; same registrable domain only. (3) Extract schema.org `Product`/`Offer` from JSON-LD/microdata (price, priceCurrency, availability, gtin/mpn/sku, seller), fall back to Open Graph `product:price:amount`; capture a screenshot hash for audit. (4) Match identity: GTIN/MPN equality with the Shopify variant's barcode/SKU (merchant must have barcodes), else title similarity ≥ threshold and same brand → "weak match" (menu-level concession only). (5) Compute landed price: competitor price + shipping (from `OfferShippingDetails` if present, else merchant-configured assumption) vs this store's; apply merchant rules (only listed competitor domains; in-stock only; no marketplaces/third-party sellers; no coupons/refurbished; cap at X% below own price; floor). (6) Cache per URL 10 min; store evidence for the merchant.
- **Abuse**: fake pages on attacker domains → allowlist/denylist + domain age/reputation; manipulated JSON-LD on real sites is unlikely; replay of a stale sale → freshness check; many URLs → per-caller caps. This mirrors retailers' price-match policies (inferred best practice, not sourced).
- **Cheap test**: run the verifier against 20 competitor product pages for the demo category and measure extraction accuracy; no agent needed.
- **Confidence**: 0.7.

### M7. Checkout-page offer affordance for page-reading browser agents (checkout UI extension)

- **Steps**: app checkout UI extension (target `purchase.checkout.block.render` or reductions) shows: "Shopping for someone with an AI agent? Pick a priority: [Faster shipping] [Lower price (price match)] [Easier returns]". A click calls the app (extension network access) → Desk → code → `applyDiscountCodeChange({type:'addDiscountCode', code})`; totals update on the page the agent and the human see. A text field accepts a competing URL.
- **Agent-side**: a browser agent that reads the DOM and clicks (Muse/Dots/Grok Bot when they use the store's own checkout; ChatGPT in-app browser; humans). Not reachable through Checkout WebMCP tools ("don't cover app-defined checkout extension interactions") and Shopify's agents.md tells WebMCP agents not to operate page controls — so this is for DOM-operating agents only.
- **Shopify-side**: checkout UI extensions (any plan for the information/reductions blocks on Shopify checkout; not rendered in Meta/Copilot direct checkout; not with Apple/Google Pay accelerated checkouts).
- **Discovery**: on-page, at the decisive moment; no prior knowledge needed.
- **Proof/abuse**: Verifier; same code rules.
- **Cheap test**: dev store; drive Grok Bot/Dots through the storefront to checkout and see whether they click the affordance when the user asked for "best deal"/"fastest shipping".
- **Confidence**: 0.5 (works for humans certainly; agent click-through unknown).
- **Unverified**: block placement options on non-Plus stores; agents' willingness to click promotional UI.

### M8. `agents.md` as the front door (discovery layer; merchant action)

- **Steps**: app ships a ready `templates/agents.md.liquid` that re-renders Shopify's default sections using the `agents` object and adds "## Conditional offers for agents" with the Desk URL, the HTTP/MCP tool names, the public menu codes, and the rule "never apply a code the user did not benefit from"; a deep link opens the theme code editor; the app checks `/agents.md` and warns the merchant if the section is missing or Shopify's default changed (diff against Shopify's current default fetched from a fresh dev store).
- **Agent-side**: agents that read `/agents.md`/`/llms.txt` at task start (Shopify's own default tells them it exists; Grok/Claude/ChatGPT web fetchers commonly read llms.txt; Muse/Dots unknown).
- **Shopify-side**: merchant edits theme (apps cannot add templates); content must be hardcoded because the Liquid context is restricted.
- **Risks**: replacing Shopify's managed file means drift as Shopify updates it; `agents.md` is cached broadly; must not include private data.
- **Cheap test**: add the template on a dev store; confirm `/agents.md`, `/llms.txt`, `/llms-full.txt` all serve it; then ask each agent "how can I get a better deal at this store?" and see whether it cites the section.
- **Confidence**: 0.8 that it serves; 0.3 that agents act on it.

### M9. `context.eligibility` claim → provisional discount (idea D)

- **Steps**: agent sends `context.eligibility: ["com.offerad.priority.speed"]` (or a verified-offer claim `com.offerad.offer.<id>`); Shopify would need to map the claim to the app's DF (not among Function inputs) or surface it as a provisional automatic discount (Shopify-side logic). Today Shopify documents no merchant/app registration of claims.
- **Agent-side**: agents send claims only for memberships their user holds; a priority is not an eligibility claim — semantic mismatch with the spec ("Buyer claims about eligible benefits such as loyalty membership, payment instrument perks").
- **Cheap test**: on a dev store, send a custom claim in `create_cart` and inspect `messages[]` (`eligibility_not_accepted`?) and whether anything reaches webhooks/Functions.
- **Confidence**: 0.1 today; the right long-term ask to Shopify is "let apps register eligibility claims that map to a Discount Function input".

### M10. Vendor UCP extension `com.offerad.offer` with Actions (idea E), or OfferAd as a separate UCP business

- **Steps**: publish schema at `https://offerad.example/ucp/schemas/offer.json`; extension extends cart/checkout; Action type `com.offerad.offer.respond` carries the offer; agent profiles declare it. **Blocked**: Shopify generates the store profile and will not list a third-party extension; agents would not declare it. Alternative: OfferAd runs its own UCP business endpoint per store (`offerad.example/{shop}/.well-known/ucp`) offering `dev.ucp.common.ask` + the offer extension, but it cannot own the Shopify checkout, so the hand-off is again a code/permalink → this collapses into M1/M2 with a different discovery story (agents discover UCP businesses via the store's own `/.well-known/ucp`, which Shopify controls).
- **Confidence**: 0.05 without Shopify's cooperation; this is the partnership/standards path (UCP contributor EP; Shopify's "eligibility" hook).

### M11. Draft order / invoice link for the negotiated price (idea F)

- **Steps**: Desk creates `draftOrderCreate` with `appliedDiscount`, custom shipping line (free express), custom gift line at $0, `note`, `tags`, `email`; `draftOrderInvoiceSend` or return `invoiceUrl`; agent opens the invoice URL (a Shopify checkout) and completes.
- **Agent-side**: browser agents and humans only — Checkout WebMCP registers no tools on draft orders; UCP Checkout MCP cannot address it. Fine for B2B/bulk-tier negotiations where a human finishes.
- **Abuse**: prices are set by the Desk; no codes to share; invoice bound to email.
- **Confidence**: 0.6 for the browser-agent/human case; wrong tool for Muse's native path.

### M12. Next-order concessions: credit, extended returns, delivery guarantee (promise now, grant after)

- **Steps**: Desk returns a signed promise ("$10 store credit after delivery", "returns extended to 60 days", "delivered by Friday or shipping refunded") embedded in the same offer token/code; DF adds a $0 "OfferAd promise" message or the code's title encodes it; after `orders/create`/`fulfillments/update` webhooks the app executes: `storeCreditAccountCredit` (customer id, amount, `expiresAt`), order tag `returns-60d` honoured by the merchant's returns app, shipping refund via `refundCreate` if the carrier date is missed. The agent can later apply credit through `declared_fields.store_credit` (Checkout WebMCP) or on the page.
- **Agent-side**: must value a promise; present it to the user as "merchant promise, enforced by OfferAd app"; weaker than an immediate total change but non-dilutive for the merchant.
- **Shopify-side**: `write_store_credit_account_transactions`, `write_orders`; customer record needed for credit (create from checkout email on order).
- **Cheap test**: dev store: grant credit via API after a test order and confirm it appears at the next checkout.
- **Confidence**: 0.6 mechanically; agent valuation unknown.

### M13. Platform offer feeds as sinks (not Shopify-native)

- Export the merchant's *public menu* (M3) as promotions to the Stripe promotion feed (if the merchant sells through Stripe ACS) and as Google Direct Offers (Google Ads pilot), and as `sale_price` windows in feeds. This is how ChatGPT-via-Stripe and Google AI Mode shoppers would see offers today; it does not carry proof or priority and is platform-ranked. Shopify merchants reach Google through the Google & YouTube channel, so a Shopify app could at most configure Google Ads Direct Offers through the Ads API on the merchant's behalf (scope creep). Note for strategy, not for build.

### Rejected
- **Automatic-discount title as a message channel** ("Agents: visit /apps/offerad"): shows on every cart, but Muse's connector rules and all agents' data-not-instructions posture make an imperative title useless; also costs 1 of 25 automatic slots. Keep titles descriptive of the saving only.
- **Cart/Checkout Validation Function as a messenger**: blocks checkout for everyone; agents would read it as an error. No.
- **URL redirect to fake `/.well-known/poppy.json` or `agent-card.json`**: redirects only fire on 404 paths and Shopify likely reserves `/.well-known`; even if it worked it would misrepresent the store's declared agent surface. Do not do it without Shopify's knowledge; test only to learn.

## 4. Part 3 — Ranking and build-first

Ranking by (a) works today without any platform's permission, (b) reaches the agents that matter (Muse, Dots, Grok Bot, plus UCP agents), (c) preserves OfferAd's thesis (seller limits in code, proof-triggered conditional offers, non-discount concessions), (d) cost to test:

1. **M1 Offer Desk (app proxy MCP + single-use code + DF)** with **M3's public menu as fallback** and **M6 verifier** inside it — the only shape that satisfies all four owner requirements (price shown by Shopify; the Desk learns priority/proof; verifies the link itself; answers with any concession that then applies via the universal code sink). Honest limit: depends on an agent calling a store-authored URL; Shopify-domain hosting (app proxy) and read-only semantics reduce but do not remove that policy barrier.
2. **M2 Buyer-side connector** — highest likelihood of actual *use* by Muse/Grok/ChatGPT/Claude users (the user installed it; platforms say the agent uses connectors automatically when relevant) and the only route into Muse's native Meta checkout beyond description text; same backend as M1; limited by distribution and review. Build immediately after M1's probe; test with the owner's own Grok custom connector first.
3. **M3 Menu alone** — ships in a day, agent-compatible everywhere, but it is a menu, not an offer engine; it is the fallback inside M1.
4. **M7 Checkout affordance** — strong for DOM-operating agents and humans at the decisive moment; does not exist in Meta direct checkout.
5. **M4 Identity-keyed deal** — elegant (no code), potentially works in Meta direct checkout via automatic discounts, but hinges on an untested resolution step.
6. **M5 Attribute token** — good for browser agents and hand-offs; invisible to pure MCP flows.
7. **M12 Next-order concessions** — differentiating non-discount layer; add once M1 works.
8. **M8 agents.md** — discovery, not a mechanism; cheap; do it with M1.
9. **M11 Draft orders** — niche (B2B/bulk).
10. **M9 eligibility claims**, **M10 vendor extension** — the "official road", closed today; prepare the ask to Shopify (register app eligibility claims → Function input; allow apps to contribute an `agents.md` section and a UCP `links[]`/`policies[]` entry).

**Build first: M1.** Why: it is the smallest system that delivers the owner's four requirements on any Shopify plan without asking Shopify, Meta, OpenAI or xAI for anything; every later mechanism (connector, checkout affordance, identity-keyed deal, next-order credits) reuses its three parts (Desk with verifier and limits, offer-code minting, Discount Function). Its first week is a *measurement*: the one-day probe tells us whether any acting agent follows store-authored pointers (the project's recorded untested assumption from 7 Oct). If no agent calls the Desk, the same code ships as the M2 connector and the merchant-side pointers become "or install the OfferAd connector" — the test, not the build, decides the distribution route.

Order of cheap tests (each ≤ 1 day, all need a Shopify partner account + dev store, which the project still lacks):
1. Admin-created code → usable in a UCP `update_cart.discounts.codes` within how many seconds; DF rejection text appears in `messages[].content`; DF `message` appears as `discounts.applied[].title`.
2. App proxy serves JSON-RPC MCP (`initialize`, `tools/list`, `tools/call`) at `/apps/offerad/mcp`.
3. Description-footer + agents.md probe with Grok Bot, Dots, Muse (owner's accounts; stop at approval; never buy).
4. Grok custom connector probe (M2) on the same dev store.
5. Guest `buyer.email` → `buyerIdentity.customer` resolution in DF input (M4).
6. Permalink `attributes[offerad]` persistence into checkout (M5).
7. WebMCP `registerTool` from an app embed shows in Chrome's tool inspector (M1b).

## 5. Things the brief missed or should restate

- `/agents.md` (+ `/llms.txt`, `/llms-full.txt`) exists on every Shopify store, is Shopify-written, and a merchant may replace it with `agents.md.liquid` — a sanctioned discovery channel, but store-level and all-or-nothing, with a restricted Liquid context (no metafields).
- Shopify tells agents in that file to use Web Bot Auth and the provided tools and *not* to script page controls — so WebMCP agents will not click an app's buttons; DOM-operating agents (Muse/Dots/Grok Bot) are a different population with different rules.
- Muse's Shopify purchases are designed to happen inside Meta's Shopify-powered direct checkout (US/CA/MX), where discount codes and Functions work but no theme/app UI exists; description text is the only merchant-authored content Muse sees there.
- Muse has a reviewed connector platform with explicit anti-fake-discount and disclosure rules; Grok adds any public MCP URL as a connector and "can use the connector's tools automatically"; Dots require plugin permission per action. The buyer-side connector is viable on all of them, with Muse gated by review.
- UCP's A2A binding allows natural-language business agents, but Shopify advertises only MCP and embedded transports — the conversational route is not closed by UCP, it is closed by Shopify's profile.
- PAP/Poppy (draft 9 Oct) adds `/.well-known/poppy.json` with MCP/OpenAPI/website/agent channels and payments later; Shopify and Stripe are partners; no store serves it yet; apps cannot write `/.well-known`.
- Stripe already states "AI agents actively offer promotions to shoppers" and ships a promotion feed with `automatic|promotion_code` redemption; Google's Direct Offers is an ads pilot; both are static merchant-published offers — OfferAd's conditional/proof-triggered layer is absent from all of them.
- Shopify discount mechanics that make the design concrete: one app code discount per offer (`usageLimit 1`, `endsAt`, metafield with the offer token) avoids code pools; the 25-active limit is for automatic discounts only; custom rejection messages render as checkout warning banners; checkout UI extensions can apply codes programmatically; Cart Transform `lineExpand` (any plan) can add a $0 gift component; store credit can be granted by API and applied via `declared_fields.store_credit`.
- The acting agents' approval cards are the real "ad slot": the human sees merchant, total, and the discount title before approving; the offer title text is the only line of copy OfferAd controls there.
